# wsp-005 · Polyrepo detected → refuse + print conversion plan; `.git` never touched

- **Status:** ✅ done · closed 2026-07-27 · **Depends on:** —

## What was missing

`docs/workspace.md` §10.3–10.4 and `CONSTITUTION.md` (2026-07-27) already specified the policy
and `references/polyrepo-convert.md` already documented the procedure — but nothing in
`generateWorkspace` actually detected the condition. A workspace root with a member carrying its
own `.git` generated normally, with no signal that the git-backed checks (drift, `git log
--grep` attribution, knowledge-graph hooks) would silently pass rather than fail.

## Fix

`detectMemberGitRoots(root, members)` (new, in `workspace.mjs`) checks each non-missing member
path for a `.git` (directory or gitlink file — both count, `existsSync` doesn't need to
distinguish which) and, if found, best-effort reads its `origin` remote via the existing
`runProbe` pattern. **Detection only** — it never touches, deletes, or rewrites anything.

Wired into `generateWorkspace` right after members are resolved, before any writer runs
(`hoistMembers` is the first thing that writes). If any member has its own `.git`, refuse:
name every such member and its remote, state that conversion is irreversible for that member's
independent remote, point at `polyrepo-convert.md` for the decision test and exact commands,
and note the alternative — keep polyrepo, but don't cite drift/attribution checks as evidence.

**No `--migrate` escape**, unlike `wsp-003`/`wsp-004`. Converting polyrepo to a monorepo is git
surgery (`git subtree add`, retiring remotes), not content classification — a categorically
different operation, entirely the user's call per the constitution's destructive-vs-additive
line. Gated on `!dryRun`, matching the existing foreign-harness check's convention: dry-run
previews the full file plan regardless of a refusal state.

## A real bug found while building this

An existing test (`wsp-001`'s hoist test) used `initGit(memberDir)` purely so `git config
user.name` would resolve deterministically for that directory — not to simulate polyrepo. It
accidentally gave the member its own `.git`, which this row now correctly refuses. Fixed the
fixture to match `ws-009`'s pattern instead: git lives at the root only, and the member's
`git config user.name` resolves by walking up to the root's config — the same as a real
monorepo subdirectory, with no `.git` of its own. No assertion in that test depended on the
member having independent git identity, so nothing was lost.

This wasn't a false positive in the new check — it's a correct refusal. Hoisting a member's
harness *files* doesn't fix the underlying git-identity problem: that member's future commits
are still invisible to root history whether or not its `AGENTS.md` gets hoisted. The user must
resolve git topology first; hoist naturally applies afterward, once the member's `.git` is gone.
